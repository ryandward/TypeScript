any
kind: soundness

Claim. If the lab accepts a program, no value of type any is used as more than unknown: it flows only into a
slot that accepts every value, and no operation that needs a structure is applied to it.

The oracle. A value of type any can be every value there is, null, undefined and 42 among them. If the checker
accepts a node, running that node must not throw a TypeError, so the checker may accept only what every value
allows. That is unknown's answer, and TypeScript already gives it for unknown at every node below.

Counterexample in plain TypeScript. any is both top and bottom. It relates to every type, in
isSimpleTypeRelatedTo, and every operation on it is accepted by a shortcut of its own; checker.ts calls
isTypeAny 51 times. A property read returns any at the isAnyLike branch of
checkPropertyAccessExpressionOrQualifiedName, without looking the property up. A call takes
isUntypedFunctionCall to resolveUntypedCall, whose anySignature takes any arguments and returns any. for-of and
spread get any back from checkIteratedTypeOrElementType. The release accepts every witness below, and Node
crashes on each.

Obligation 1, assignability: TS2898
  Statement. A value of type S may flow into a slot of type T only if every value of S is a T. Every value is
  a value of any, so an any source may flow only into a slot that accepts every value: unknown, any, or a union
  such as {} | null | undefined. The same holds for an any inside a type, as in any[] or Promise<any>.
  Mechanism. Under valueAssignableRelation, isSimpleTypeRelatedTo relates an any source, and an any that
  checkExpression read as unknown, only to those targets, and reports TS2898 for any other.
  Why it suffices. Every flow of a value into a slot is judged under valueAssignableRelation: an initializer,
  an assignment, a return, an argument. An any nested in a type argument reaches the same branch, because type
  arguments are related through their variances under the same relation.
  In Lean. ../../lean/Top.lean proves that, with covariant readonly arrays, contravariant parameters and record
  depth, rejecting any at the leaf is enough. It refutes subDown, any assignable to every type, four ways:
  directly, through an array's element, through a callback's parameter, and through a record field inside a
  parameter, none of them postulated at the container. Promise<any> isn't in the calculus, and functions there
  take one argument, so a rest parameter or a second parameter is covered only by analogy.
  Witnesses:
    flow-typeof-function.ts            typeof 'function' keeps an object type callable, and its call gives any
    rel-erased-overload-target.ts      an erased generic signature, (x: any) => any, held as two overloads
    rel-any-nested-promise.ts          then(JSON.parse)'s Promise<any> held as a Promise of an interface
    rel-any-declared-promise.ts        a function declared to return Promise<any>, awaited into an interface
    lib-then-json-parse.ts             then(JSON.parse) infers Promise<any>
    lib-object-values-interface.ts     Object.values on an interface returns any[]
    lib-promise-any-errors.ts          AggregateError.errors is any[]
    lib-generator-tnext-any.ts         yield is any when Generator's TNext is left to its default
    lib-allsettled-reason-any.ts       a callback claims a record for PromiseRejectedResult's reason: any
    chk-any-nested-constraint.ts       an any inside a constraint's parameter type, which the body passes a string
  Controls:
    unknown-checked.ts                 an any flowing into unknown, decided by typeof before it is read
  Rejected sound code, because soundness forces it:
    json-parse-number.ts               the text is a number, but only a parser could say so

Obligation 3, a parameter typed any: TS2920
  Statement. A function relates to a function type whose parameter is typed any only if its own parameter takes
  unknown, in every relation. A parameter typed any says its caller may pass anything, and a type parameter's
  constraint makes the generic body such a caller.
  Mechanism. compareSignaturesRelated compares a target parameter that is any itself (isAnyParameterType, not
  errorType or an instantiation's wildcard) as unknown, and relates every other parameter as a value flow too,
  under valueAssignableRelation, so an any nested in it is refused as well; either failure reports TS2920. A
  constraint refused this way reaches the program through inference, which falls back to the constraint, and the
  argument's flow into it then reports TS2898 (chk-any-nested-constraint, cited under obligation 1).
  The library's utility types bound a function by (...args: never) => unknown instead, which takes no argument
  list at all, so every function satisfies it.
  Why it suffices. Every relation between function types compares parameters in compareSignaturesRelated, so no
  relation lets a parameter typed any vouch for a narrower one.
  In Lean. ../../lean/mutants/subDown.callback-param, refuted under obligation 1, is this route in the calculus:
  any assignable to a callback's parameter.
  Witnesses:
    lib-promise-catch-annotated.ts     catch hands its callback reason: any
    lib-promise-any-errors.ts          the same, the callback annotated AggregateError
    lib-json-stringify-replacer.ts     stringify hands its replacer value: any
    lib-string-replace-callback.ts     replace hands its callback ...args: any[]
    chk-any-constraint-call.ts         a function of a number under F extends (a: any) => unknown, called with a
                                       string
  Rejected sound code, because a constraint's any parameter promises the function anything:
    function-constraint.ts             a function of a number under F extends (...args: any[]) => any, never called

Obligation 2, structure: TS2900
  Statement. An operation that needs its operand to have a structure may be accepted only if every value of
  the operand's type has it: a property or an element to read, a call or construct signature, an iterator, an
  object for destructuring or `in` to look into, a callable right side for instanceof. null and 42 are values
  of any, and they have none of these.
  Mechanism. checkExpression gives a value of type any the type uncheckedType: an intrinsic with unknown's
  flags and its own identity, the way errorType and wildcardType are any with theirs. Each operation then meets
  an unknown and rejects it the way TypeScript rejects unknown. Where TypeScript reports that, TS2900 heads the
  chain, with TypeScript's own diagnostic beneath it:
    checkNonNullTypeWithReporter       TS18046   property read, element read, call, new, for-of, in
    getPropertyTypeForIndexType        TS2339    object destructuring
    reportTypeNotIterableError         TS2488    array spread, call spread, array destructuring
    invocationError                    TS2349    tagged template
    resolveInstanceofExpression        TS2359    instanceof
  getBindingElementTypeFromParentType reads a parent of type any as uncheckedType too, so a nested destructuring
  pattern, whose parent is a property's type and never an expression, is judged the same way.
  The mark survives the two operations that would otherwise drop it: getNonNullableType keeps it through an
  optional chain or ??, and getUnionType keeps it in a union through IncludesUnchecked.
  Why it suffices. Every one of these operations takes its operand's type from checkExpression: directly,
  through checkNonNullExpression, or through checkExpressionCached for the initializer that destructuring
  takes apart. So no operand of type any reaches an operation's own shortcut; it arrives as unknown.
  In Lean. ../../lean/Top.lean proves that a Top with no structural operations, which is unknown, can't crash, in
  a calculus with records, arrays, functions and one constructor, so instanceof has a sound rule to compare
  against. Each of any's permissions added back to Top is refuted by a well-typed program that crashes:
  projTop for a property read and destructuring, elemTop, appTop for a call and a tagged template, iterTop,
  spreadTop, inTop and instOfTop. new isn't in the calculus. It also proves the other half of the claim: a
  parser from Top to { name: string }, built from the checks L asks for (a plain-object test, in, and typeof on
  the field bound to a name), never gets stuck on any value.
  Witnesses:
    chk-destructure-nested-any.ts      a nested pattern takes apart an iterator result's value: any
    rule-any.ts                        a value typed any read as a string
    chk-property-off-any.ts            a property read off null
    chk-element-off-any.ts             an element read off null
    chk-call-any.ts                    a call on 42
    chk-new-any.ts                     new on 42
    chk-tagged-template-any.ts         42 as a template tag
    chk-iterate-any.ts                 for-of over 42
    chk-spread-any.ts                  an array spread of 42
    chk-destructure-any.ts             destructuring null
    chk-in-any.ts                      in with 42 on the right
    chk-instanceof-any.ts              instanceof with 42 on the right
  Controls:
    narrowed-before-use.ts             typeof decides the value before it is read
  Rejected sound code, because L's record model chooses it:
    optional-read.ts                   null?.length doesn't throw, but L's records are closed, so a read
                                       needs a label the type has
