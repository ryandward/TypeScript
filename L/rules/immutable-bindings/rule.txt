immutable-bindings
kind: soundness

Claim. If the lab accepts a program, every binding is assigned exactly once, where it is declared, so its value
is always the one it was declared with. The keyword doesn't matter: let, var and const are held to the same
rule. L-hooks bans let and var by name instead.

Counterexample in plain TypeScript. A let or var may be declared without a value and assigned later.
TypeScript assumes a variable read inside another function is initialized if it is assigned anywhere, so a
hoisted function can read it while it is still undefined, and the program crashes on a value its type says is
a string.

Obligation 1, binding without an initializer: TS2892
  Statement. Every binding the program creates gets its value where it is declared.
  Mechanism. checkGrammarVariableDeclaration reports TS2892 for a let or var declared without an initializer,
  in the same check that already requires one of const and using. Loop, catch and ambient bindings aren't held
  to it: the loop or the throw binds them, and an ambient declaration describes a binding made elsewhere.
  Why it suffices. A declaration is the only place a binding is created, and every declaration either carries
  a value or is one of those three. A binding with a value from its declaration on can't be read before it
  has one, which closes the crash.
  Witnesses:
    chk-captured-let.ts                the declaration without a value
  Controls:
    ambient-declaration.ts             declare var describes a global that already exists
    catch-binding.ts                   a catch variable, bound by the throw
    for-of-binding.ts                  a for-of variable, bound by the loop

Obligation 2, assignment to a binding: TS2893
  Statement. No binding is assigned after its declaration. Soundness doesn't need this half: TypeScript's types
  stay honest when a binding is reassigned. L forbids it so that a binding means one value.
  Mechanism. checkIdentifier reports TS2893 for any assignment to a variable after its declaration, parameters
  included, in the same place it already rejects an assignment to a const.
  Why it suffices. Every assignment to a binding, plain, compound, increment or destructuring, resolves its
  target through checkIdentifier, which sees that it is being assigned.
  Witnesses:
    flow-destructure-param-reassign.ts the same, through a destructured alias
    flow-alias-param-reassign.ts       a parameter reassigned while an alias of its tag stays narrowed
    flow-alias-closure.ts              a parameter reassigned before a closure reads its narrowed alias
    chk-captured-let.ts                the assignment after the declaration, which TypeScript took as proof
                                       the read was initialized
  Controls:
    let-never-reassigned.ts            a let with an initializer, never assigned again
  Rejected sound code, because L forbids reassignment even where it is safe:
    counting-loop.ts                   a counting loop reassigns its counter on every step
