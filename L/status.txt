WHAT CHANGED TODAY, AND WHY

The lab had been crashing on ordinary code, in two ways, both in how the foundation commit wired the value
relation into overload resolution. While a context-sensitive argument is skipped, chooseOverload checks
stand-ins: a placeholder for each skipped function, and object literals stripped of their freshness. The value
relation judged those stand-ins and rejected the candidate, then the reporting pass found no error and hit
"No error for last overload signature". Separately, the re-check of the subtype pass's winner discarded a
candidate that chooseOverload had already replaced with its instantiation, and the pass that followed asserted
on arity. I moved both checks inside chooseOverload: the provisional pass uses plain assignability, as the
release does, and the subtype pass's winner gets checked as a value before it's accepted (fadc61c80).

Fresh array literals had been exempted in checkArrayLiteral, by retyping the literal to the expected element
type. That was expression typing serving a soundness rule, which breaks locality: retyping an expression
changes what inference reads. I put checkArrayLiteral back to the release and moved the exemption into the
relation, next to the object literal one (e5795182f).

The back-check's old error said "Type 'string' is not assignable to type 'string | number'", which is false as
worded, and the array witnesses were being reported through concat and slice().pop() instead of the writable
index signature that makes Array invariant. Every writable position now goes through one helper, relatedBack,
which reports TS2890, and a type argument that a writable position made invariant gets TS2891 (e5795182f).

For let and var, I first tried a definite-assignment patch in flow analysis. Doing that without rejecting safe
code would take cross-function call-order analysis, which TypeScript left out on purpose because it's
intractable, so I reverted it. A token ban replaced it briefly, and then single-assignment semantics replaced
the ban: every binding is initialized where it's declared (TS2892), and nothing assigns to a variable afterward
(TS2893). That states the property L actually wants, which is that bindings never change. It also means
`let x = compute()` with no later reassignment compiles. I left isReadonlySymbol alone on purpose, because
narrowing reads constness and treating variables as constants there would reach into flow analysis
(dbe09f6e5).

The tracker now requires each rejection to carry its mechanism's code, and all L material lives under L/
(cbc662b51).


GENOMEHUB

GenomeHub is only a source of diagnostics here. I compared the lab with the release on its lines changed since
its merge base with main (570af7906), with GenomeHub at 17863bb8 plus its agent's uncommitted edits. The lab
rejects 76 lines there that the release accepts:

  33  TS2890  writable position
  12  TS2891  write-induced invariance
   9  TS2892  binding without an initializer
  18  TS2893  assignment to a binding
   4  no L mechanism in the chain

The four with no L mechanism are all `app.use(express.json())` in integration tests:

  packages/server/src/__tests__/lib/egress.integration.test.ts:132
  packages/server/src/__tests__/routes/host_key_pinning.integration.test.ts:53
  packages/server/src/__tests__/routes/parquet_url_retry_budget.integration.test.ts:28
  packages/server/src/__tests__/routes/write_gates.integration.test.ts:101

I traced the first one through overload resolution, and the overload report is masking an L failure. It's not
a relation bug. The release picks use(...handlers: RequestHandler[]). The lab rejects that overload with TS2890
on req.originalUrl: connect's IncomingMessage declares `originalUrl?: string | undefined`, optional and
writable, while Express's Request declares `originalUrl: string`. Every candidate fails, and when more than
three do, TypeScript reports only the last one, which complains about PathParams. The relation is right by the
rule: through connect's type, a handler could store undefined in a field Express promises is a string. That's
two libraries' contracts colliding, so by the boundary rule it gets stopped and reported.

The eleven errors we'd called unexplained all trace to an L mechanism now: s3.ts (3), file_lifecycle.ts:316,
in_turn.ts:5, uploads.ts's ZodError lines (3) and the roles-handler tests. Tracing to a mechanism only proves
the rejection comes through the rule. It doesn't make each verdict right for GenomeHub. The s3.ts three reject
`httpAgent: Agent` against a writable `Agent | AgentOptions` field in the AWS SDK's config, which is a library
contract, so that one gets stopped and reported too.

The categories we sorted out before today still stand. zod schemas get fixed in our model by keeping each
schema's own type instead of widening it. TypeORM's mapped partial forces the relation, so it gets stopped and
reported. slice() results passed into TypeORM options get fixed by declaring the source with the element type
its consumer takes. Map viewed as ReadonlyMap was fixed in the lab's lib. Error.name narrowed in a subclass gets
fixed in our model. The readonly IsComplete objects are true positives by the rule.
